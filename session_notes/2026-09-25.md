What killed reuse was a second axis the code diff cannot see: the partials record
`r_version = 4.5.1` (this workstation) and O2 runs **R 4.4.2** with a different
BLAS. This study's own `local/combine.R` hard-errors on a result set mixing
`r_version`/`pkg_version` ("numerics are not comparable across builds"), and the
`setup-cluster-simulations` provenance contract says the same. Worse, the 236 cover
only **12 of 36 configs, all at λ ∈ {0.010, 0.020, 0.035}** — entirely inside the
interior regime, which is precisely the segment the study uses as a falsifiable
check against the closed-form `Corr_K(τ_S, τ_Y)`. Reusing them would have put a
build artifact exactly where a theory violation would be read. Discarding costs
~236 units ≈ 5.6 O2 CPU-hours. The files are left on disk untouched.

**Rep scoping was the one real structural problem.** `canonical-validation` slices
tasks by absolute unit id because it runs all of `unit_table()`. lambda-sweep
declares `TOTAL_REPS = 40` but executes reps 1–20, and `unit_table()` enumerates
rep-fastest within config — so reps 1–20 are **not** a contiguous unit range, they
are 36 interleaved blocks of 20 spanning unit ids 1…1420. Copying the reference
slicing would have silently run reps 21–40. `slurm/run_replication.R` therefore
slices the row index of the *rep-filtered* table while still naming partials by the
true global `unit` id (`%06d`, matching `local/run_local.R` so ids are comparable
across backends). `slurm/validate_mapping.R` proves it before any cluster time:
for `reps_per_job` ∈ {1,3,5,7,12,20,37,60,100,720} the tasks cover the 720 in-scope
units exactly once, no duplicates, nothing out of scope. Since the task→unit map
depends on `(GRID, TOTAL_REPS, REP_FROM, REP_TO)`, `submit.sh` writes a `REP_SCOPE`
file into scratch and `combine.R` refuses to assert coverage against a scope that
disagrees with it.

**Sizing came from a real cluster array, not a local estimate.** `canonical-validation`
sized off a local 61.4 s/unit and then saw 191.8–254.6 s/unit on O2 — a 3.8×
underestimate, in the direction that times out every task. So
`slurm/profile_timing.R` now *refuses* to write sizing from a local profile unless
explicitly overridden, and `submit.sh --smoke N` submits a real `sbatch` array. The
probe rows are picked to straddle the grid rather than taken contiguously, because
the rep-filtered table is config-major and tasks 1–8 would otherwise all be dgp1 at
λ = 0.01. Smoke run `smoke-20260925-150832_b049ad1` (job `54417881`, 8 units, one
per DGP × λ ∈ {0.01, 0.30}): **8/8 COMPLETED, 0 errors, median 68.1 s, q0.9 85.2 s,
max 85.7 s.** Notably that is ~1.5× local (local dgp5 λ=0.01 was 45.4 s), *not* the
3.8× the sibling study saw — the ratio is study-specific, which is the argument for
measuring it. λ = 0.01 costs ~25% more than λ = 0.30 because the adaptive sampler
settles at M_final = 1500 there rather than 1200.

Sizing on **q0.9 = 85.2 s/unit** (not the median: a task's wall time is the sum of
its block, so the tail binds): `reps_per_job = floor(3600/85.2) = 42`,
`total_tasks = ceil(720/42) = 18`, est 0.99 hr/task, `--time = ceil(3578 × 1.5) =
0-01:29:31` (the same 1.5× safety canonical-validation used), `--mem 2G`.
`--target-hours 1` rather than 2 because with only 720 units all 18 tasks run
concurrently and finish in about one task's wall time; 1 hr is the floor of the
scaffold's 1–3 hr window, so still inside convention. `--mem 2G` is the floor, not a
measurement — `sizing.json` records `"peak_gb": null` honestly — but it is
evidence-backed: the local profile peaked ~0.6 GB, matching canonical-validation's
measured 0.589 GB at identical n and sampler settings, and that study ran 4000
units at 2G without OOM.

**The 1.5× time safety factor is what saved the run, and that is the transferable
lesson.** The 8-unit smoke predicted the *median* almost perfectly (68.1 s vs 67.2 s
over all 720) but badly understated the *tail*: full-run q0.9 was **118.5 s** against
the smoke's 85.2 s (~1.4× low) and the max **269.2 s** against 85.7 s (~3.1× low) —
node contention plus the adaptive sampler occasionally running to a larger `M_final`.
Sizing on q0.9 = 85.2 s gave 0.99 hr/task estimated; the `--time 0-01:29:31` the
1.5× bought is precisely what kept the heavy-tail tasks inside the wall clock. At the
bare estimate they would have timed out. So: a small probe is enough to size the
*centre*, not the tail — keep TIME_SAFETY, and do not pack a larger `reps_per_job`
off a small probe's q0.9 without it.
